# Record and crate edit conflicts

Editors capture an independent opening baseline, including the complete `updated_at` string. Saving sends only fields changed against that baseline and requires the same persisted version. Cloud repositories apply owner, ID and version filters in one UPDATE. Browser repositories check the version inside the IndexedDB write transaction. An explicit null version matches only a null stored version; omitted preconditions retain the existing internal command behavior. Demo mutations remain read-only.

When another session has changed the entity, the store rolls back only its own optimistic fields and fetches a new authoritative snapshot. The dialog retains typed values and pending cover selection, displays the latest changed metadata, and disables Save until the user chooses “Keep my edits and review”. Review merges deliberate edits with the latest unedited values and advances the baseline. A second concurrent write can cause another conflict; review never bypasses the precondition. Failed transport does not reset the crate form.

Crate membership remains outside editor metadata and continues through the existing atomic membership RPCs. A membership write advances the crate version and can require metadata review. Account/workspace changes, dialog closure, a different selection, and superseded submissions suppress late completions.

The migration `20261024070000_make_record_edit_versions_monotonic.sql` gives records a timestamp trigger equivalent to the established crate/track version guarantees. Every UPDATE advances the record token, including repeated updates in one transaction. Apply this migration before releasing the new editor bundle. It adds no column and leaves existing clients compatible.

A rejected cover update preserves the specific repository conflict outcome. The coordinator reconciles its unique uploaded candidate against an authoritative cover-path read before cleanup. It removes only an unreferenced candidate; uncertain responses or failed reconciliation preserve the object for later cleanup. It never drains the old-cover queue as if a rejected save had committed. Local cover writes and version checks are one IndexedDB transaction, so a rejected write cannot add or delete a managed cover.

Coverage includes full-precision/null cloud filters and owner enforcement; database monotonicity and stale-write rejection; store refreshes, optimistic rollback and membership preservation; input/cover preservation and reviewed retry; transport failure and a reopened dialog; local adapter atomicity; and two independent browser sessions against real local Supabase for record and crate conflicts. Integration fixture cleanup removes only the run's disposable accounts and owned data. The developer database is migrated in place and is never reset by this work.
